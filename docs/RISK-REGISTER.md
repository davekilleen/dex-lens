| RISK-MAC-SOCKET-CREATION | macOS Seatbelt blocks outbound connection, not socket creation, on GitHub macos-14 runners and on local Apple Silicon Macs. | CI runs 31244515811, 31244792823, and 31244920768 showed AF_INET, AF_INET6, and AF_UNIX sockets were created under the shipped profile despite `(deny system-socket)`, while the runtime proof returned `connect-denied`, `write-open-denied`, and `exec-denied`. Reproduced locally on macOS 26 / Apple Silicon on 2026-08-21. | The macOS containment story is asymmetric with Linux: no egress is enforced, but "no socket fd can exist" is not proven on the pilot platform. | **Accepted asymmetry (2026-08-21).** `MacOSStrategy.availability()` requires a fresh runtime tuple proving no-write, no-exec, and no-network, where the no-network proof is satisfied by either `socket-denied` or `connect-denied`. Egress needs `connect`/`sendto`, and `prove_containment` aborts the collection if a connection succeeds or fails ambiguously, so the guarantee the product makes to a person — nothing leaves this machine — is proven either way. The honest label is carried through to `ContainmentOutcome.proofs` and shown verbatim, never relabelled as `socket-denied`. Keep `(deny system-socket)` plus `(deny network*)` and retain the direct egress probe. | Dave | Closed — accepted |
| RISK-BOUNDED-CAPTURE-ABSENCE | A bounded capture reported `absent` for artifacts it had simply never reached, and the presence probes reported `healthy` while describing an arbitrary fraction of the approved scope. | First real-machine run, 2026-08-21: a 170k-file vault admitted 151k files, the 2048-file bound was spent on the walk order, and 149,020 admitted files were never read. The probes reported healthy on 1.4% of scope. Only `collection-exclusions` disclosed the truncation. | The product's central promise is that an assumption never masquerades as proof. Claiming absence from an unread remainder reports a capability the person **has** as one they lack, and it does so with the highest confidence label the product offers. | Capture is ordered so files named in `CLAUDE_CODE_DIAGNOSTIC_BASENAMES` are read before the bound bites (order only — the approved scope is unchanged); the file-count bound is raised to 16384 so `max_total_bytes` is again what binds; and a presence probe on an incomplete capture reports `could-not-check` with `blocked` evidence instead of `absent`, so the finding surfaces as Unknown. Partial results carry the caveat in `detail`. | Dave | Closed — fixed |
| RISK-MAC-INTERPRETER-LITERAL | The Seatbelt exec allowlist named an unresolved interpreter path, so the contained child was denied on any Mac whose Python is symlinked. | Homebrew's `sys.base_prefix` is `/opt/homebrew/opt/python@3.X/...`, a symlink into `/opt/homebrew/Cellar/...`. Found on 2026-08-21 during the first real-machine run against a live vault. | Every Homebrew-Python Mac — the common case — silently lost the deep adapter and fell back to the guided path, which reads nothing. | RISK-WOW-GATE-SCORES-SHAPE | The Wow Gate scores whether a ledger has the right shape, not whether its claims are supported, so a fabricated diagnosis outscores an honest one. | Independent review, 2026-09-03, reproduced at `45ceca5`. A ledger with all fourteen expectations `UNKNOWN` and evidence-free, zero observations, and every insight citing a fabricated evidence id scored **95/100, passed, zero hard failures** through the shipped `scripts/run_wow_gate.py`. An honest run with three real recommendations and genuinely assessed families scored **84 and failed**. Causes: `wow_gate.py:58-76` scores `UNKNOWN` identically to the five determinate states; `:49-55` tests a condition `WorkflowEdge.evidence_ids = Field(min_length=2)` already guarantees; `:101-114` never reduces for absent evidence; `:79-89` awards 8 points for zero recommendations. Separately `manual-proposal` (`:131`) is unreachable because `WorkReceipt.submission_route` is `Literal["engine-work-packet"]` (`work.py:318`), and three of the plan's nine hard-failure classes are unimplemented. | The gate is the programme's only measure of whether the autonomous diagnosis works. While it scores shape, no run's number is evidence, and the acceptance bar of "90 or better" cannot be met meaningfully. | **Open.** Task 1 of `docs/superpowers/plans/2026-09-03-dex-lens-trustworthy-first-number.md`. No private evaluation should be run until it lands. | Dave | Open |
| RISK-GUIDED-COMPARE-TRUSTS-ARTIFACT | Guided comparison reads back the stored `reconciled-proposals` artifact and only shape-validates it, instead of re-deriving it from the receipts it just reconciled. | Independent review, 2026-09-03, reproduced at `45ceca5`. Replacing the artifact on a run at `ANALYSIS_COMPLETED` with 20 fabricated `worth-borrowing` recommendations citing an evidence token never minted for the run was accepted into the ledger — against a cap of 10. `orchestrator.py:797-805` uses `ValidatedProposal.model_validate`, which checks none of what `validate_proposal` checks. The identical `_put` manipulation one artifact earlier is already covered by `test_guided_work_fails_closed_for_tampered_stored_diagnosis_input` and correctly fails closed. | Every upstream tamper-evidence guard the engine builds — re-derived queue, recomputed response digests, packet binding — is bypassable at the one artifact that actually reaches the ledger. The product's central claim is that conclusions are evidence-bound. | The guided branch of `_compare_ledger` now re-derives the final proposal set from the validated response records via `_final_reconciled_proposals` — the same derivation `_complete_analysis` performs, extracted into one shared helper so the two paths cannot drift — and refuses with a typed `DiagnosisStateError` when the stored `reconciled-proposals` artifact differs from the re-derived set in any way, added or dropped, before any ledger artifact is written. | RISK-GUIDED-RUN-WEDGE | Aggregate proposal limits are enforced only after every specialist receipt is already final, so an ordinary run can reach a terminal state with no exit. | Independent review, 2026-09-03, reproduced at `45ceca5`. Eight normal specialists each citing two distinct engine-minted evidence tokens for the same candidate — each response individually accepted — exceeds `MAX_EVIDENCE_IDS = 8` (`orchestrator.py:1218`) when the sceptical packet's context is built. `submit_work` then raises before the retry is recorded, `advance` refuses as incomplete, and `work` returns the same packet indefinitely. The `MAX_RECOMMENDATIONS = 10` variant (`:1238`) wedges identically. | This is normal specialist behaviour, not an attack: citing two pieces of evidence is what a good specialist does. A wedged run cannot be completed or abandoned cleanly, and the failure surfaces as a raw pydantic error rather than a typed refusal. | Evidence unions are truncated, over-cap recommendations are refused at submission. When agreeing proposals for one candidate together cite more than `MAX_EVIDENCE_IDS` distinct tokens, the reconciled result cites exactly the first 8 of the sorted union — deterministic and order-independent; evidence breadth is corroboration, so no conclusion is lost. Applied wherever evidence is unioned across agreeing proposals: `_normal_reconciled_proposals` (orchestrator) and `_coalesce_group` (specialists). The `MAX_RECOMMENDATIONS` cap is enforced at `submit_work`: a normal response that would push the distinct recommendation-candidate count over 10 is treated as a malformed specialist response — it burns the bounded attempt, is recorded as an empty rejection, and raises the typed retry message; an exact replay of an accepted response stays idempotent because the prospective count excludes the packet's own receipts. The reconciliation-time cap check remains as a fail-closed backstop against tampered stores; an honest run can no longer reach it. Both wedges reproduced through the real engine and observed to close after the fix. | Dave | Closed — fixed |
